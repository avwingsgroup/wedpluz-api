# Backend architecture

The Wedpluz API is a single Laravel 13 application (PHP 8.3+) that serves the web app, the Android and iOS apps, and the admin console from one versioned REST surface at `/api/v1`. It implements the contract in [backend-handoff/](backend-handoff/) — `openapi.yaml` is the source of truth for paths, payloads and status codes.

| Concern | Choice |
|---|---|
| Runtime | PHP 8.3+ (tested on 8.5), Laravel 13 |
| Database | PostgreSQL 15+ (tested on 18), `pg_trgm` for fuzzy search, `tsvector` for event search |
| Cache, queues, locks, rate limits | Redis (predis client by default; phpredis optional) |
| Auth | Laravel Sanctum personal access tokens + rotating refresh tokens |
| Realtime | Laravel Reverb (Pusher protocol), optional |
| Files | Cloudinary for public media; local disk or S3 for private files |
| PDFs | dompdf (tickets, receipts, report exports) |
| Tests | Pest on a real PostgreSQL database |

---

## 1. Request lifecycle

```
Client ──► nginx/LB ──► public/index.php
             │
             ▼
   RequestContext          correlation id (X-Correlation-Id), client platform/version into log context
   HandleCors              config/cors.php
   throttle:<limiter>      login / otp / customer / admin / public / webhooks / suggestions
   auth:sanctum            bearer token → User or AdminUser (token expiry + admin idle timeout)
   audience:customer|admin token must belong to the right model and carry the right ability
   permission:<key>        admin RBAC (one permission per admin route)
   admin.audit             fallback audit row for any admin write not audited explicitly
   idempotent              Idempotency-Key replay for payment-sensitive writes
             │
             ▼
   Controller (thin)  ──►  Form Request (validation, camelCase fields, human attribute names)
             │
             ▼
   Service (domain logic, transactions, row locks)  ──►  Integrations (providers)
             │
             ▼
   Presenter → contract JSON  { data, message? } | { data, meta } | cursor meta
   Errors    → ApiExceptionRenderer → { message, code, errors?, correlationId }
```

Every response carries `X-Correlation-Id`; every error body repeats it as `correlationId`, and log lines include it, so a support ticket can be traced end to end.

## 2. Code layout

```
app/
  Enums/                  status enums, AdminPermission catalogue (32 keys + default roles)
  Events/RealtimeBroadcast.php   single ShouldBroadcast event, dotted names (message.created…)
  Exceptions/             ApiException (domain errors with contract codes), ApiExceptionRenderer
  Http/
    Controllers/Api/V1/   customer + public controllers
    Controllers/Api/V1/Admin/  admin console controllers
    Middleware/           RequestContext, EnsureAudience, RequireAdminPermission, Idempotent, …
    Requests/             Form Requests (ApiRequest base, shared Rules)
  Integrations/           provider clients behind interfaces (see integrations.md)
    Payments/  Sms/  WhatsApp/  Push/  Media/  Identity/  Mail/  Auth/  Live/  Ai/  Support/
  Jobs/                   queued work (webhooks, payouts, notifications, exports, …)
  Models/                 ~100 Eloquent models, prefixed ULID keys
  Services/               domain services, one folder per module
    Auth Users Events Checkout Payments Finance Wallet Subscriptions Vendors
    Communities Messaging Notifications Moderation Media Planner Platform Admin Realtime
  Support/                Money, Sql, ListQuery, RichText, XlsxWriter, Fmt, Codes, Platform
routes/
  api.php                 health, auth, then requires the files below
  api/public.php          unauthenticated catalogue (events, vendors, plans, CMS, settings)
  api/customer.php        customer surface (+ customer_social.php)
  api/admin.php           admin console (every route names its permission)
  api/webhooks.php        provider callbacks
  channels.php            realtime channel authorisation
  console.php             artisan commands + scheduler
```

**Controllers are thin.** They resolve the actor, call one service method, and hand the result to a presenter. Business rules live in services so jobs, the scheduler and controllers share one implementation.

**Presenters, not API Resources.** Each module has a presenter (`EventPresenter`, `TicketPresenter`, `AdminPresenter`, …) that maps models to the exact contract shapes, eager-loads what it needs in batches (no N+1), and varies output by viewer (owner vs. public, admin vs. customer).

## 3. Identifiers and data conventions

- **Primary keys** are prefixed ULIDs stored as `varchar(40)`: `usr_01J…`, `evt_…`, `ord_…`, `tik_…`, `pay_…`. Prefixes make IDs self-describing in logs and support tickets, and ULIDs sort by creation time. Generated by the `HasPrefixedId` trait.
- **Polymorphic types** use an enforced morph map (`user`, `admin_user`, `order`, `wallet_transaction`, `subscription_payment`, …), never class names.
- **Money** is integer minor units (kobo) everywhere — columns, payloads and ledger. `App\Support\Money` is the only conversion point.
- **Time** is stored in UTC (`timestamptz`); the platform display timezone is `Africa/Lagos` (`WEDPLUZ_TIMEZONE`).
- **JSON** request and response fields are camelCase; columns are snake_case.
- **Mass assignment.** The base model is unguarded, so services always map validated fields explicitly — request payloads are never passed straight to `create()`/`update()`.

## 4. Authentication and authorisation

| Audience | Token model | Ability | Access TTL | Refresh |
|---|---|---|---|---|
| Customer | `User` | `customer` | 60 min | 30 days, rotating |
| Admin | `AdminUser` | `admin` | 8 h absolute, 30 min idle | none (sign in again) |

- **Refresh tokens** are stored hashed, rotate on every use, and belong to a *family* (one sign-in on one device). Reusing an already-rotated refresh token revokes the whole family (theft detection). A family is what `/me/sessions` lists as a "session".
- **Customer sign-in:** email + password (`POST /auth/login`) or Google (`POST /auth/social` with an ID token, verified against Google's JWKS and `GOOGLE_CLIENT_IDS`). One-time codes (4 digits, 10 minutes, 5 attempts) verify email, reset passwords and set up the wallet PIN; they go by email, and also by SMS when the phone is verified and `smsOtpEnabled` is on.
- **Admin sign-in:** password, then TOTP (RFC 6238, ±1 step, replay-protected per step). Payout approval needs a fresh TOTP code and a different admin from the creator (four-eyes, also enforced by a DB check constraint).
- **Event-level roles** (`EventAccess`): organiser > manager (full or partial with permissions such as `manage_guests`, `scan_tickets`, `view_revenue`) > assigned vendor. Unauthorised access to a managed event returns 404 so existence does not leak.
- **Admin RBAC:** 32 permission keys, 7 seeded system roles, custom roles. Admins cannot grant permissions they do not hold. Denials are written to `security_logs`.
- **Plan gating** (`PlanGate`): premium features (sub-events, planner AI, design generation) return `402 PAYMENT_REQUIRED` on the free plan.

## 5. Checkout, payments and fulfilment

```
POST /checkout/quotes   server prices lines (tickets, seats, food, promo, fees) → quote (10 min)
POST /orders            Idempotency-Key; lock ticket types; place inventory holds + seat
                        reservations; create order (awaiting_payment) + payment; initialise
                        provider → checkout URL / wallet debit / free issue
        │
        ├── provider webhook ─► verify signature ─► dedupe (provider, event id) ─► store
        │                       ─► ProcessWebhookJob (critical queue)
        │                       ─► WebhookRouter re-queries the provider (never trusts the body)
        └── GET /orders/{id}/verify-payment (return page) ─► same provider re-query
                                    │
                                    ▼
                     FulfillmentService::applyVerification  (idempotent, order row lock)
                     amount/currency must match → else alert + hold
                     sold += qty conditionally (oversold → roll back, auto-refund)
                     issue tickets + signed QR, ledger posting, receipts, notifications
```

- **The client's view of payment status is never trusted.** Only a provider re-query (`verify`) moves an order to `paid`.
- **Inventory** is protected by `SELECT … FOR UPDATE` on ticket types, a conditional `sold` increment, and a partial unique index on active seat reservations (`SEAT_TAKEN`).
- **Expiry:** a scheduler task expires unpaid orders after the hold window, but asks the provider one last time first, so a late success is fulfilled rather than lost.
- **Refunds** go back to the original method (or wallet); amounts at or above `REFUND_APPROVAL_THRESHOLD` wait for admin approval.

## 6. Ledger, wallet, settlements and payouts

All money movement is recorded in an **append-only double-entry ledger** (`ledger_entries`). `LedgerService::post` refuses unbalanced postings and postings outside a DB transaction, and updates cached wallet balances in the same transaction (a check constraint keeps them non-negative).

| Account | Meaning |
|---|---|
| `provider:<name>` | money held at a payment provider |
| `wallet:<id>` / `wallet_pending:<id>` | customer wallet available / pending balances |
| `organizer_payable:<userId>` | ticket revenue owed to an organiser |
| `platform:fees` / `platform:commission` | Wedpluz revenue |
| `subscriptions:revenue` | plan revenue |
| `promoter_payable` | promoter commissions |
| `withdrawals_in_transit` / `payouts_in_transit` | transfers sent, not yet confirmed |

- **Wallet:** top-up through a provider, PIN-protected withdrawals (lockout after 5 attempts), daily limit, max 3 bank accounts, 48 h cooldown after a bank change before payouts.
- **Settlements:** when an event completes, a settlement is created per organiser and becomes eligible after `payments.settlementDelayDays` (admin setting, default 3). Open disputes or unverified identity hold it.
- **Payouts:** created by one admin, approved by another with a fresh TOTP code, executed by `ExecutePayoutJob`, confirmed by transfer webhooks.
- **Reconciliation:** a daily job re-queries providers for succeeded payments and flags mismatches as critical alerts.

## 7. Background processing

Queues run on Redis, in their own Redis DB (`REDIS_QUEUE_DB`, default 2) so flushing the cache never drops jobs. Jobs dispatched inside a DB transaction are held until it commits (`after_commit`).

| Connection / queue | Jobs | Why separate |
|---|---|---|
| `redis` / `critical` | ProcessWebhookJob, ExecuteWithdrawalJob, ExecutePayoutJob | money movement; must not wait behind bulk work |
| `redis` / `notifications` | DeliverNotificationJob, NotifyEventUpdatedJob | user-facing latency |
| `redis` / `broadcasts` | RealtimeBroadcast | realtime fan-out |
| `redis` / `default` | VerifyIdentityJob, queued mail | general |
| `redis` / `low` | SendCampaignChunkJob, ImportRemoteImageJob | bulk work |
| `redis-long` / `long` | CancelEventJob (up to 15 min), RunExportJob, GenerateDesignJob | long jobs need a `retry_after` (960 s) far above the fast connection's (180 s); keeping them apart means a crashed fast job is retried within 3 minutes |

Run one worker per connection:

```bash
php artisan queue:work redis --queue=critical,notifications,broadcasts,default,low --sleep=1 --timeout=150
php artisan queue:work redis-long --queue=long --timeout=930
```

The fast worker serves five queues in priority order, so it uses a non-blocking pop with `--sleep=1` (a blocking pop on `critical` would delay every lower queue); the single-queue long worker uses a blocking pop. Every job sets an explicit `$timeout` below its connection's `retry_after`, so a slow job is never handed to a second worker while still running. Jobs are idempotent (row locks, unique keys, `dedupe_key`) so retries are safe.

**Health.** Workers write a heartbeat on every loop and the scheduler once a minute. `GET /api/v1/health` reports database, Redis, cache, queue and scheduler (`503` only when a critical dependency is down; `degraded` when workers or the scheduler stall). `GET /api/v1/health/details` (header `X-Health-Token`) adds latencies, queue depths, failed jobs, heartbeat ages, storage and configured integrations. `php artisan wedpluz:health --ping-queue` pushes a probe job through each connection and waits for a worker to run it.

The scheduler (`routes/console.php`) runs on exactly one host (`onOneServer` uses a Redis lock):

| Command | Cadence | Purpose |
|---|---|---|
| `wedpluz:expire-orders` | every minute | expire unpaid orders after a final provider check, release holds |
| `wedpluz:dispatch-campaigns` | every minute | start scheduled notification campaigns |
| `wedpluz:complete-events` | 15 min | complete ended events, open settlements |
| `wedpluz:event-reminders` | 15 min | 24 h and 2 h reminders (deduplicated) |
| `wedpluz:warm-metrics` | 10 min | admin dashboard cache |
| `wedpluz:promote-settlements` | hourly | pending → ready |
| `wedpluz:renew-subscriptions` | hourly | renew, downgrade, expire |
| `wedpluz:archive-communities` | hourly | archive communities of cancelled events |
| `wedpluz:process-deletions` | daily 02:00 WAT | anonymise accounts after the 30-day grace period |
| `wedpluz:reconcile` | daily 03:00 WAT | provider reconciliation |
| `wedpluz:purge` | daily 04:00 WAT | retention: unattached uploads, status media, identity selfies (90 d), expired exports, stale keys and tokens |

## 8. Notifications

`NotificationService::notify($user, $templateKey, …)` writes an in-app row (`notifications`) and one `notification_deliveries` row per channel (email, SMS, WhatsApp, push) according to the user's preferences, each with a `dedupe_key` so retries and repeated triggers never double-send. `DeliverNotificationJob` renders the template (admin-editable in `notification_templates`, with code defaults in `DefaultTemplates`) and sends through the channel's provider. Transactional messages (receipts, OTPs, security) always go by email regardless of marketing preferences. Hard bounces and complaints from ZeptoMail land in `email_suppressions`.

## 9. Realtime

Realtime is optional (`BROADCAST_CONNECTION=reverb` turns it on). Services call `Realtime::emit($channels, 'message.created', $payload)`, which dispatches one queued `RealtimeBroadcast` after the DB transaction commits. Payloads use the REST shapes, delivery is at-most-once, and clients refetch on reconnect. Channel authorisation (`POST /api/v1/broadcasting/auth`) is in `routes/channels.php`:

| Channel | Who |
|---|---|
| `private-user.{id}` | that customer |
| `private-conversation.{id}` / `presence-conversation.{id}` | participants (community members for community chats) |
| `private-community.{id}` | members |
| `private-event.{id}.manage` | organiser and managers with `manage_guests` or `scan_tickets` |
| `private-admin` | any active admin |
| `private-admin.moderation` | admins with `moderation.view` |

## 10. Cross-cutting safeguards

- **Idempotency:** `Idempotency-Key` on order creation, wallet top-up and withdrawal, and subscription checkout. The key is scoped to user + endpoint; the same key with a different body returns `409`, an in-flight duplicate returns `409`, a completed one replays the stored response.
- **Webhooks:** signature verified first (HMAC/SHA-512 for Paystack and Monnify, Stripe `t=,v1=` with 5-minute tolerance, PayPal verify-signature API, Flutterwave `verif-hash`, Meta `X-Hub-Signature-256`, HMAC-SHA512 for Prembly, shared secrets for Termii and ZeptoMail, Twilio `X-Twilio-Signature`). Failures are written to `security_logs`; duplicates are acknowledged with `200` and ignored.
- **Audit:** every admin write produces an `audit_logs` row (actor, action, target, before/after, IP, user agent).
- **Integration logs:** every provider call is logged with operation, status and latency, with secrets and PII redacted; logs feed the admin gateway-health panel.
- **Rate limits:** per IP + identifier for login and OTP, per user for customer and admin APIs, per provider for webhooks; `429 RATE_LIMITED` with `Retry-After`.
- **Rich text** is sanitised on write against an allow-list (`RichText`).
- **Private files** (identity selfies, exports, documents) live on the private disk and are served only through short-lived signed URLs.
